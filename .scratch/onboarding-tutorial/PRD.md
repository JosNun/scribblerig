# PRD: Onboarding tutorial — a playable demo scene that teaches every type

Status: done

## Parent

`.scratch/scribblerig/PRD.md`

## Depends on

[`.scratch/text-object/PRD.md`](../text-object/PRD.md) — the tutorial's
in-scene callouts are text bodies. Ship that first.

## Problem

A new user lands on ScribbleRig with an empty room. The palette shows
Ball, Platform, Spawner; the connectors strip shows Spring, Motor,
Weld, Pin. **Nothing on the screen explains what those things do, what
they're for, or what's interesting to build with them.** Tooltips help
a little (commit on issue 25), but a tooltip can't show what a *spring*
behaves like, or what happens when you point a motor at a wheel — you
have to actually build a thing.

This is the "blank canvas" problem. The fix isn't another tooltip; it's
a starter scene that's already interesting and self-explanatory.

## Solution

A pre-built **tutorial scene** that loads as the first-ever build on a
new tab, and is re-summonable from the Builds list:

- **Single playable Rube-Goldberg chain.** One contraption that uses
  every body type (ball, platform, spawner) and every connector type
  (spring, motor, weld, pin) in a chain reaction. Press Play and
  something fun happens.
- **In-scene callouts via text bodies.** Each piece has a short text
  label next to it: "← motor — drag the speed slider while it's
  running", "← spawner — opens to edit what it spits out". The
  text-object feature is the vehicle for these annotations.
- **"Show tutorial" button in the Builds modal head.** Mints a fresh
  copy of the tutorial as a new build every time. So a user who
  scrambled their first copy can always get a clean one.

The tutorial is **a normal build**, not a special mode. It has a
session id in the Builds list, autosaves on edit, can be deleted,
renamed, shared like anything else. The user's first interaction is
poking at a working contraption — not staring at a blank room.

## User Stories

1. As a first-time visitor, I want to land on a working example rather
   than an empty room, so that I can see what the app is for in five
   seconds.
2. As a first-time visitor, I want to press Play and watch the example
   do something interesting, so that I understand what the simulation
   looks like.
3. As a first-time visitor, I want each part of the example labeled in
   the scene itself, so that I can match the palette terms ("motor",
   "spring") to actual visible things.
4. As a returning visitor, I want to be able to summon the tutorial
   again later from the Builds list, so that I can refer back to it
   without losing whatever I'm currently working on.
5. As a returning visitor, I want a *fresh* copy of the tutorial each
   time I press "Show tutorial", so that whatever I scribbled on
   yesterday's copy doesn't pollute today's reference.
6. As a returning visitor with autosaved work, I don't want the
   tutorial shoved at me again on every page reload, so that my own
   builds stay the default.
7. As a tinkerer using the tutorial as a reference, I want to edit it
   freely — drag pieces around, change props, save my version — so
   that the tutorial is a starting point, not a read-only display.

## Implementation Decisions

### What the chain actually does

A loose sketch — the agent has authoring latitude as long as every
type appears and the chain is **legible** (you can follow what causes
what). Suggested flow, top-left to bottom-right:

1. **Spawner** drops a ball onto…
2. **Platform** angled as a ramp (rotated). Ball rolls down to…
3. **Pin'd lever** — a platform pinned at its center, with a heavy
   ball welded to one end. Ball hitting the long arm tips it,
   swinging the welded ball into…
4. **Spring** — a spring connected between a wall-pinned point and a
   ball. The lever's swung ball strikes the spring-loaded ball,
   launching it onto…
5. **Motor-driven wheel** — a ball pinned through its centre with a
   motor revolute joint, spinning continuously. The launched ball
   lands on a platform behind the spinning wheel — the wheel acts as
   a flipper / pinball-style nudge that knocks the ball into…
6. **Final platform** — the "goal" surface. Ball comes to rest here.

Text callouts (six to ten of them) sit next to each piece:

- "Spawner → opens to edit what it emits"
- "Platforms can be rotated and made static"
- "Pin = swivels freely; Weld = locks rigidly"
- "Spring — adjust stiffness in the panel"
- "Motor — change speed live (while running)"
- A title label at top: "Welcome to ScribbleRig — press Play. Then
  tinker."

The author should playtest the chain until it runs the full sequence
on Play without divergence on same-machine Reset (ADR-0003 — fixed
timestep gives this for free).

### Trigger

`bootSession` in `src/share/storage.ts` today resolves a tab's starting
scene by: shared URL → tab's autosaved session → lazy fork of
most-recent build → fresh blank scene.

Insert one new step **before "fresh blank scene"**:

> If the user has **no shared scene** AND **no sessions at all** (not
> just no most-recent — truly empty list), seed a new session from
> the tutorial scene constant. Title it "Tutorial". That session goes
> through the normal first-edit autosave path, so it materialises on
> the user's first interaction (consistent with how a lazily-forked
> "new build" works today).

Users with autosaved builds — including anyone who's been here before
— skip this. The check is **list-empty, not list-has-tutorial**, so
deleting the tutorial doesn't re-seed it on the next reload.

### "Show tutorial" button

A button in the Builds modal head (next to "+ New build"). Clicking
it:

1. Mints a fresh session id (same as `+ New build`).
2. Adopts the tutorial scene into that session.
3. Closes the Builds modal and switches the tab to the new build.

Each press = a **fresh copy**. If a user already has a "Tutorial"
session, the new one might land as "Tutorial (2)" via the existing
title-uniquing logic (`share/sessions.ts`) — that's the expected
behaviour and matches the user story.

The button is **always visible** in the modal, even when the user
has builds in their list. A small affordance ("Open a fresh
tutorial") accompanies it so it's clear what'll happen.

### Where the tutorial scene lives

A new file: `src/share/tutorialScene.ts`. Exports a `Scene` literal
(typed against `src/scene/scene.ts`'s `Scene`). Hand-authored as a
nested object, not encoded — it's a build-time constant, not a
runtime payload. Authoring is just easier in source than in
base64url; tweaks during playtesting are normal git diffs.

```ts
// src/share/tutorialScene.ts
import type { Scene } from "../scene/scene";

export const TUTORIAL_TITLE = "Tutorial";

export const tutorialScene: Scene = {
  version: 1,
  nextId: 42, // bump to one past the highest id used below
  title: TUTORIAL_TITLE,
  rooms: [
    {
      settings: { gravity: { x: 0, y: 9.81 }, /* … */ },
      bodies: [
        { id: "b1", type: "platform", /* … */ },
        { id: "b2", type: "text", props: { text: "← motor — change speed live", size: 0.35 }, /* … */ },
        // …all the bodies + text callouts
      ],
      connectors: [
        { id: "c1", type: "motor", a: { /* … */ }, b: { /* … */ }, props: { /* … */ } },
        // …
      ],
    },
  ],
};
```

Author the scene incrementally **in the running app**: build it
manually, copy the share URL, decode the payload, paste it into
`tutorialScene.ts`, then iterate in source as needed. The result is
a hand-tuned scene with stable ids and no encoded blob.

### "Show tutorial" plumbing

`src/share/storage.ts` gains:

```ts
export function newTutorialBuild(): { id: string; scene: Scene } {
  const id = mintSessionId();
  const scene = structuredClone(tutorialScene);
  saveSession(id, scene, /* thumbnail */ null);
  adoptSession(id);
  return { id, scene };
}
```

`src/App.tsx`'s Builds modal calls `newTutorialBuild()` then
`adoptScene` (existing helper) on the returned scene, exactly the
same way `startNewBuild` does today.

### What if `text` body type isn't merged yet

The tutorial PRD **depends on** text-object. Don't try to ship the
tutorial without text first; the scene literal would type-error or
the labels would just be absent. If the agent picks this up before
text-object is in, leave a tracking comment and pause.

### Thumbnail

The Builds list renders a thumbnail per session. The tutorial's
thumbnail is computed the same way as any other build — first save
runs `renderThumbnail(scene)` in `App.tsx`. Nothing special needed.

### Determinism

The chain depends on Reset replaying identically (ADR-0003). The
author **must verify** that on their machine, fresh Reset → fresh
Play reproduces the same sequence each time. If the chain is fragile
(piece A barely clears piece B 50% of the time), retune until it's
robust. A best-effort replay is the product's core promise; the
tutorial is the highest-visibility place it shows up.

### Localization

English text only. No i18n in v1.

## Tests

- `share/codec` — `encode(decode(tutorialScene))` round-trips (catches
  authoring drift if someone edits the literal in a way the codec
  can't represent).
- `share/storage` — first-visit boot on a fresh tab loads the
  tutorial; second visit with autosaved sessions does NOT re-seed.
- `share/sessions` — minting a second tutorial when one already
  exists produces a unique title.
- Manual:
  - Open a fresh incognito tab → tutorial loads as the starting
    build.
  - Open Builds modal → "Show tutorial" button is visible.
  - Press "Show tutorial" → new build named "Tutorial" (or "Tutorial
    (2)") opens.
  - Press Play on the tutorial scene → the full chain reaction
    runs without divergence on Reset → Play.
  - Delete the tutorial build → reload → tutorial does **not**
    re-seed (we have other sessions; list isn't empty).

## Out of Scope

- **Multi-step guided tour** (overlay tooltips that walk the user
  through "click this, now drag that"). The in-scene callouts via
  text bodies are the entire tutorial mechanism. No app-mode for
  guided steps.
- **Interactive checklist / progress.** No "you've used spring,
  motor, weld — keep going!" UI.
- **Multiple tutorial scenes / chapters.** One scene.
- **Localization** (English only).
- **Auto-Play on first load.** The user presses Play — that's part
  of the moment of discovery.

## Notes

- The single biggest authoring risk is the chain being **fragile**.
  Spend time on robustness — wide margins, contact normals that don't
  glance off, simple geometries that don't need lucky bounces. A
  tutorial that "usually works" undermines trust in the engine.
- Sister insight: a well-tuned tutorial doubles as a **regression
  test for the physics chain**. The Reset-replay test above is the
  formal version of that.
- If someone later wants a deeper tutorial system (chapters, a
  built-in guide overlay, etc.), this PRD's "single playable demo
  scene" model is a strict subset — they can be added without
  reworking what we ship here.
