# PRD: Text object — labels and notes in a scene

Status: ready-for-agent

## Parent

`.scratch/scribblerig/PRD.md`

## Problem

Today the only thing a builder can put on the canvas is a body (ball,
platform, spawner) or a connector (spring, motor, weld, pin). There is
no way to **annotate** a build — to drop a label next to a motor saying
"try cranking the speed", to leave a note explaining what the spawner
is doing, or to call out the goal of a contraption. That gap matters in
two places:

1. **Authoring own builds.** Users who share a build over a URL have no
   in-scene way to explain it. The recipient sees the contraption with
   no context.
2. **The forthcoming onboarding tutorial.**
   [`.scratch/onboarding-tutorial/PRD.md`](../onboarding-tutorial/PRD.md)
   needs to call out parts of a pre-built scene ("← this is a motor —
   change its speed") and a text object is the obvious vehicle.

A new top-level entity (separate from bodies + connectors) would force
a parallel rendering, serialization, picking, and copy/paste path. A
**non-colliding body type** rides the existing rails for ~free.

## Solution

A `text` body type. Placed from the palette like any other body; its
position, rotation, drag, copy/paste, delete, share, and undo behaviour
all reuse the existing body plumbing. It contributes **nothing** to the
physics — the `sim` compile step skips it.

It carries a single `text` string prop the user edits in the
PropertyPanel. The renderer draws it as bare ink Mynerve text over the
paper background; no doodle box, no hatch fill, no bounding shape. The
only chrome a text body shows is the same dashed selection rectangle
every body gets when selected.

A text body is **visible in both Build and Run modes** — labels are
just as useful at runtime as during authoring. It cannot be a connector
endpoint (snap targets continue to be physical bodies / world points
only).

## User Stories

1. As a tinkerer, I want to drop a text label into a scene, so that I
   can annotate parts of my build.
2. As a tinkerer, I want to edit a label's text in the property panel,
   so that I can type and revise without entering a separate mode.
3. As a tinkerer, I want to move and rotate a text label like any other
   body, so that I can place it neatly next to whatever it labels.
4. As a tinkerer, I want a text label to be visible while the
   simulation runs, so that my annotations stay readable in Run mode.
5. As a tinkerer, I want to share a build that includes text labels and
   have a recipient see the same labels, so that my notes travel with
   the scene.
6. As a recipient, I want labels in a shared build to read cleanly in
   the same hand-drawn style as everything else, so that they don't
   feel bolted on.

## Implementation Decisions

### Domain model — non-colliding body type

Text lives in `rooms[i].bodies[]` as a body whose `type === "text"`.
The existing scene shape, share-codec, history, copy/paste, and editor
hit-testing all work unchanged.

The current glossary in [`CONTEXT.md`](../../CONTEXT.md) says **"Bodies
are the only things that collide"** and **"Body — has mass and a
collision shape."** That contradicts a non-colliding body type. The
PRD softens this:

> Body — has a position and rotation on the room. **Most body types
> (ball, platform, spawner) also have mass and a collision shape;
> text is the exception — a body that participates only in rendering
> and selection, never in collisions.**

The doc edit is part of this PRD's scope. No ADR required.

### Registry entry

A new entry in `src/registry/registry.ts`:

```ts
text: {
  label: "Text",
  defaults: { text: "Label", size: 0.4, static: true },
  propSchema: [
    { key: "text", kind: "string", label: "Text",
      placeholder: "Type a label…", multiline: true },
    { key: "size", kind: "number", label: "Size",
      min: 0.15, max: 1.5, step: 0.05, unit: "m" },
  ],
  shapes(props): [],     // no collider — sim skips it
  anchors(props): [],    // no anchors — connectors can't bind here
  // Renderer uses a dedicated path keyed on type === "text"; `shapes`
  // staying empty means body hit-testing needs a parallel branch
  // (see `editor` below).
  style: { stroke: INK, fill: "transparent" },
},
```

The `static: true` default is for forward-compat with a future motion
prop — text never moves under physics today, but encoding "this is
authored, not driven" up front means tests don't need a special case.

### PropertyPanel — new `string` field kind

`src/ui/PropertyPanel.tsx` today renders `number`, `boolean`,
`vec2`-ish controls. A `string` kind is straight HTML `<textarea>` /
`<input>`. Each keystroke commits a scene mutation through the same
`mergeKey` scheme as numeric scrubs, so typing collapses into one undo
step per text body. Backspace inside the field must **not** trigger
the body-delete shortcut (the existing `typing` guard in
`App.tsx`'s `keydown` handler already covers this).

`multiline: true` selects a small textarea; otherwise a single-line
input.

### Renderer

`src/renderer/renderer.ts` gets a parallel path for `type === "text"`,
beside `drawBody`. Reuses the body's `position` + `rotation` for the
canvas transform; uses `ctx.font = '${sizePx}px Mynerve, sans-serif'`
and `ctx.fillText` (no Rough.js wobble — adding noise to text would
hurt legibility). No drawable cache (text is cheap to redraw; the
shimmer concern doesn't apply to native font).

Size prop is in **meters** — multiply by `cam.scale` for the font
size in pixels. This way zoom and the doodle ink scale together with
the body, matching world-fill behaviour for hatching (ADR-0004
spirit).

Selection chrome: the existing `drawSelection` already draws a dashed
box around a body's bounding box. For text, "bounding box" = the
measured text metrics. Compute width via `ctx.measureText` and use
the size prop for height.

The drag-back-to-palette shrink-fade (commits `75f4c27` and `6c3fc03`)
needs to also work for text bodies. The existing `drawBodyFaded`
helper wraps `drawBody` in a context scale + globalAlpha; the text
path needs the same wrapper. Symmetry not optional — the affordance
would look broken if text didn't participate.

### sim

`src/sim/sim.ts`'s `compile` step iterates `scene.rooms[0].bodies` and
creates a Rapier rigid body + collider per entry. Add an early
`continue` for `body.type === "text"`. The body's id is still
referenced by the renderer (which reads `designTransforms` directly
in Build mode and the sim's transforms map in Run mode), so we must
also seed Run-mode transforms for text bodies — easiest: have
`compile` push `{ id, transform: { position, rotation } }` into a
side-table of "static visual bodies" that `readTransforms` merges in.
Alternative: render text bodies directly from `sceneRef.current` in
Run mode (skipping the world's transform map). The side-table is
cleaner because the renderer stays uniform.

### editor

`src/editor/editor.ts`'s `bodyAtPoint` today uses each shape's
geometry from `def(type).shapes(props)`. With `shapes(): []`, text
bodies become unpickable. Add a parallel branch: for `type ===
"text"`, hit-test the measured text bounding box. The renderer
already knows how to compute that box; expose it through a small
helper (`textBoundsLocal(props): { halfW, halfH }`) called from both
the renderer and editor.

Connector snapping (`snapping/snapping.ts`) must **skip text bodies**
when looking for snap candidates — a spring should not anchor to a
label. Cheapest fix: in `snapping`, filter the candidate list by
`def(b.type).anchors(b.props).length > 0`. Text's `anchors() === []`
makes it self-exclude.

### share-codec / autosave

No work required — share/codec is already tolerant via the registry
(ADR-0008). Decoding a payload with a `text` body in a build that
doesn't know the type would drop it gracefully; once this PRD lands,
the type is recognised and round-trips cleanly.

Round-trip test: a scene with text bodies survives
`decode(encode(scene))` byte-for-byte.

### Spawner templates

A spawner's template (`spawner.template.bodies[]`) is the same
`Body[]` type as a room's bodies. A user **can** drop a text body
into a spawner template — the template would then emit text bodies at
runtime, which seems silly but harmless (each emitted label fades on
its TTL). Decide in the issue:

- **Allow it** (cheap, internally consistent) — and accept the
  silly-but-harmless emergent behaviour.
- **Block it at the UI** in `App.tsx`'s `dropBodyAtPointer` (mirroring
  the `type === "spawner"` ban for nested spawners), and sanitize on
  share-decode.

Recommendation: **block at the UI**. Spawning labels is never useful
and the precedent (nested-spawner ban) is already there.

### Selection box around variable-size text

The dashed selection rectangle is drawn around the body's bbox. Text
bbox is measured per render, so the dash size matches the rendered
text — no "selection box stuck at old size" bug.

A multi-line label measures as `max(lineWidth) × lineCount * size`.
Lines split on `\n`; no auto-wrap (Mynerve is variable-width and
auto-wrap is more UI than this needs).

## Implementation sketch

```
src/registry/registry.ts        new "text" body type + helper textBoundsLocal
src/renderer/renderer.ts        parallel drawText / drawTextFaded path
src/sim/sim.ts                  skip text in compile; visual-only transforms
src/editor/editor.ts            bodyAtPoint branch for text (uses textBoundsLocal)
src/snapping/snapping.ts        filter candidates with anchors().length > 0
src/ui/PropertyPanel.tsx        new `string` field kind (single + multiline)
src/App.tsx                     block text drops into spawner templates;
                                ensure typing-into-PropertyPanel doesn't trigger
                                the global delete/backspace shortcut (existing
                                guard should already cover, verify)
CONTEXT.md                      glossary edit (Body row — see above)
src/share/codec.test.ts         add text round-trip cases
src/registry/registry.test.ts   add text type tests
```

## Tests

- `registry` — `def("text")` returns the schema; defaults populate.
- `share/codec` — round-trip a scene with text bodies; round-trip
  preserves multiline content.
- `sim` — `compile(sceneWithText).step()` runs without creating
  Rapier bodies/colliders for the text; transform readout still
  reports the text body's position.
- `editor` — `bodyAtPoint` hits text at the measured bbox; snapping
  candidates exclude text.
- `editor` — `clampInsideRoom` works for text (uses the same bbox).
- Manual: drag a placed text label back over the palette; the
  shrink-fade affordance must apply (commits `75f4c27` and `6c3fc03`).

## Out of Scope

- **Inline canvas editing.** Property-panel editing is enough for v1.
  Double-click to focus the panel's text field is a nice-to-have but
  not required to ship.
- **Color picker for ink.** Single ink color (matches the doodle UI).
- **Font selection.** Mynerve only.
- **Attaching text to a body** (label-follows-the-ball). World-space
  only for v1.
- **Rich text** — no bold/italic/links.

## Notes

- Once text ships, the onboarding tutorial PRD becomes implementable.
- The glossary edit is small but matters — without it, a future
  reader of `CONTEXT.md` will be confused by a body that doesn't
  collide. Don't skip it.
- Performance: text rendering uses native canvas font, not Rough.js
  drawables. No cache invalidation concerns.
